* Add SharedArrayBuffer-based parallel BGZF decompression via Web Workers

Add a worker pool that parallelizes BGZF block decompression using
SharedArrayBuffer for zero-copy input sharing. Each worker receives a
contiguous byte range and calls decompressAll in a single WASM call
(reusing one Decompressor and one output Vec), matching htslib's
per-thread decompression strategy.

Key components:
- BgzfBlockScan: fast header scanner for block boundaries
- Worker pool with range-based dispatch and Transferable results
- BgzfWorkerPoolHost/Client: MessagePort-based shared pool for use
  across multiple worker contexts (e.g. JBrowse RPC workers)
- Shared singleton pool via getSharedWorkerPool()
- Puppeteer browser tests with correctness verification and benchmarks

Benchmarks (8 workers, headless Chrome):
- 0.5MB file: ~3x speedup
- 13.5MB BAM: ~2-4x speedup
- 17.8MB BAM: ~3.5x speedup
- 3 concurrent workers sharing pool: ~2.8x throughput

* Surface worker decompression failures instead of hanging

If decompressAll threw inside the worker, no message was posted back and
the caller's pending promise hung forever. Wrap the worker handler in
try/catch and post { type: 'error', batchId, message } so the host can

* feat: parallel decompression without cross-origin isolation

The worker pool required SharedArrayBuffer, which requires COOP/COEP, which
most JBrowse installs cannot set — so the feature was unreachable for the
users who would benefit from it.

Transferring an ArrayBuffer to a worker is a zero-copy MOVE and needs no
isolation, so the pool now slices each worker's range out of the input and
transfers it. SharedArrayBuffer is still used when the caller already holds
one, and nothing is copied into a fresh SAB to get there.

That last point is the measured part. Head to head in Chrome, cross-origin
isolated so both paths were available (min of 10, arms interleaved, output
verified byte-identical each rep, 4 workers):

  chunk                 transfer   SAB alloc   SAB pooled   SAB prefilled
  20MB -> 41.5MB          2.61x      2.44x       2.79x         3.42x
  8MB  -> 58.1MB          2.81x      2.77x       2.85x         3.26x
  4MB  -> 8.1MB           2.81x      2.79x       3.04x         3.73x
  2MB  -> 14.5MB          2.97x      2.94x       2.99x         3.53x

Allocating a SAB per call is slower than transferring; pooling one puts it
at parity. The reason is that decompressAll copies its input into the wasm
heap regardless, so shared memory removes the host-side slice and not the
boundary copy. Only `prefilled` — bytes already in shared memory before the
call — is meaningfully faster, and that is a property of the caller's read
path, not something this package can arrange.

On a page with no isolation at all, where the pool previously refused to
start, the same 4 workers give 2.67-2.92x (3.04-4.14x at 8).

The gate is now Worker availability rather than SharedArrayBuffer, which is
what it always meant: getSharedWorkerPool still returns undefined under node
so callers keep the sequential fallback, and createBgzfWorkerPool's error
names the real requirement.

Two behaviours worth stating because tests now pin them. The pool copies each
worker's range out rather than transferring the caller's buffer, so an input
survives the call — bam-js hands over a filehandle read it is still holding.
And the MessagePort client pays one extra copy the direct pool does not, to
own what it transfers across the hop.

Tests: a fake Worker running the real wasm pins the transferable protocol in
node CI, and a new browser page asserts the whole thing against a second
server that sends no COOP/COEP.

Also formats bgzfBlockScan.ts and unzip.ts, which were failing format:check
on this branch.

- Revert "chore: converge package.json" — the CHANGELOG prettier step

Removes `prettier --write CHANGELOG.md` from the `version` script, which the
previous commit added on a premise I did not check.

The reasoning was: git-cliff writes CHANGELOG.md after `preversion` has run, so
the format:check gate structurally cannot see it, while CI checks it on the tag
commit -- a hole the gate cannot cover. The first half is true. The second is
not: **every one of the 20 repos already lists CHANGELOG.md in
.prettierignore**, so CI's format:check skips it too and there was never a hole.

The step was also a no-op, verified rather than assumed: prettier skips an
ignored file even when it is named explicitly on the command line, so a
deliberately mangled CHANGELOG.md came back unchanged.

hclust was the only repo that had this step, which is where I copied it from.
It is reverted there too. The .prettierignore comments in bgzf-filehandle,
cram-js and hclust say why nobody should add it back: reformatting a generated
changelog fights the generator on every release.
